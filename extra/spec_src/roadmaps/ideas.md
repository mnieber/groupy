1. Add splitting, not just moving. Right now the restructure moves whole functions, but real code often mixes state changes with business logic in one function. Such a function isn't cleanly an action or a rule. The biggest structural gain comes from an "extract function" step that splits it into an action that calls rules and utils. Without that step, Claude has to force mixed functions into a single category.
2. Discover models, not just functions. The design is centred on functions, but the models layer usually has to be found in implicit data: dicts with string keys, tuples, and long parameter lists that get passed around together. A step that proposes dataclassy models for these would give the other layers something to depend on.
3. Work top-down from the entrypoints. Instead of looking at each function in isolation, start from the entrypoints (the use cases) and trace their call trees. The top-level operations become actions, and the rules and utils fall out below them. This gives Claude the context it needs to tell an action from a rule, which is hard to judge one file at a time.
4. Do the global steps once, then apply in vertical slices. Build the glossary and module layout for the whole project. Then do the rename, restructure, apply and test cycle one module or use case at a time, instead of one phase across the whole codebase. The code then works again after every slice, and each diff is small enough to review. The current approach leaves the entire codebase broken at once.
5. Add a safety net and make the apply steps deterministic. Before breaking anything, have Claude write tests that pin down current behaviour, at least for the entrypoints and actions. Combine that with apply steps that run on a deterministic refactoring library (rope/libcst), so most steps preserve behaviour and less actually breaks.
6. Reconsider whether node files should mirror the source. Per-module node files duplicate the code, which is why the sync problem exists. An alternative is to treat the code as the single source of truth, plus a few global plan files (glossary, layout, a list of moves, renames and splits). That's less state to keep consistent and easier to review as one plan.
7. Make the target structure machine-checkable. Express the rules (layer direction, one code unit per file, location rules) as lint checks, for example with import-linter. Then Breaker can measure progress, check Claude's output automatically, and you can rerun the whole process to improve the result step by step.
